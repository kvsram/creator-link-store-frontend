# Creator Link Store Frontend

React + Vite client for the Creator Store admin and public storefront. It expects the API at `http://localhost:8080` during Vite development and runs at `http://localhost:5173`.

```bash
npm install
npm test
npm run dev
```

The public product page starts at `/`, explains the supported creator flows, shows Starter and test-stage Creator Pro pricing, and links to a two-step signup at `/signup`. Signup asks for a plan, creator/business name, email, and password. Identity v1 allocates the store link, and the creator may rename it later in **Settings → Profile**. Signup then shows a pending-verification state. Registration, login, current-account lookup, and logout use only `/api/v1/auth/**`; the browser does not silently downgrade to legacy authentication endpoints. Signup and Login show the synthetic-credential warning only when the page is actually served over plain HTTP. A Creator Pro selection stores a one-hour, non-sensitive navigation reminder in that browser; successful same-browser verification consumes it and opens the Billing explanation. Cross-device verification opens the normal dashboard. Neither path creates an entitlement or charge, and no email, identity, password, or token is stored with the reminder. Creator subscription checkout remains disabled until a separate Razorpay/Stripe hosted flow and verified activation webhook are implemented. Instagram AutoDM remains a Starter test feature; Premium is limited to unavailable growth features and higher-limit positioning.

## Identity v1 frontend contract

The account UI implements `/verify-email`, `/forgot-password`, and `/reset-password`, exposes Sign out in the dashboard, and provides device-session management under **Settings → Security**. It expects these server contracts:

- `POST /api/v1/auth/registrations` with `{displayName, email, password}` plus optional `phone` or a backward-compatible explicit `handle` returns HTTP `202` and `{id, publicId, handle, displayName, status: "pending_verification", emailVerified: false, verificationRequired: true}`. If no handle is supplied, the API allocates the store link. Signup requires 12–128 Unicode code points. `testDeliveryId`, when present in a test environment, is deliberately ignored by the browser.
- `POST /api/v1/auth/email-verifications` with `{token}` verifies a one-time email token, sets the authenticated httpOnly cookie, and lets the success CTA continue without another login. It opens `/dashboard/` unless that same browser has an unexpired Creator Pro billing-page reminder. `POST /api/v1/auth/email-verifications/resend` accepts `{email}` and always returns generic accepted behavior for an eligible pending account; the UI requires a complete email and never derives it from a masked hint.
- `POST /api/v1/auth/sessions` with `{handleOrEmail, password}` sets the httpOnly session cookie and returns the authenticated account projection. A pending account should return HTTP `403` with `{code: "EMAIL_NOT_VERIFIED"}`.
- `GET /api/v1/auth/me` returns the current account projection or HTTP `401` when the session is absent or expired.
- `GET /api/v1/auth/sessions` returns `{sessions: [{publicId, current, createdAt, lastSeenAt, idleExpiresAt, expiresAt, authMethod, device, location}]}`. `authMethod` is `password` or `email_verification`. `DELETE /api/v1/auth/sessions/current` signs out this browser, and `DELETE /api/v1/auth/sessions/{publicId}` revokes another device.
- `POST /api/v1/auth/password-reset-requests` with `{email}` always returns HTTP `202`, regardless of account existence. `POST /api/v1/auth/password-resets` with `{token, newPassword}` consumes the one-time token, applies the same 12–128-character rule, and invalidates existing sessions.

The centralized API client first obtains `GET /api/v1/auth/csrf`, keeps `credentials: include`, and sends the issued token in the server-selected header (currently `X-XSRF-TOKEN`) for every unsafe API method. It refreshes the token and retries exactly once only when the server returns `403` with `CSRF_TOKEN_INVALID`; requests have bounded timeouts and structured failures. Successful non-empty API responses must be valid JSON, and signup/login/verification/current-account responses must match the complete Identity v1 account shape before the UI changes authentication state.

New verification and reset emails place the one-time value in the URL fragment (`#token=...`), which browsers do not send in the HTTP request. The client accepts legacy query-token links during migration, gives a fragment token precedence, and removes either form from the visible URL and browser history before using it. A legacy query token can already have reached edge access logs before JavaScript runs, so production log retention must still be reviewed during the migration. NGINX applies `Referrer-Policy: no-referrer` globally and `Cache-Control: no-store` only to auth-page document routes, leaving hashed assets cacheable. The frontend never stores, logs, or renders auth tokens, never fetches test-delivery records, and never sends `X-Test-Auth-Key`; test token delivery belongs to an operator-controlled test harness.

NGINX accepts forwarded client addresses only from loopback and RFC1918 proxy peers, resolves the last untrusted hop, and overwrites the header sent to the API. Production security groups must expose this container only through the intended load balancer or ingress; direct public traffic remains untrusted.

The admin starts at `/dashboard/` and implements Home, My Store, Success, Income, Analytics, Customers, Community, More, and Settings. The demo public page is `/alex`; an unknown one-segment creator route now displays a real not-found page, while server/network failures display a retry state instead of being mistaken for signup. Reserved public application routes cannot be claimed as creator handles. The UI is an original design informed by the supplied observable feature reference; it does not contain Stan source or branding.

After a public creator store loads successfully, the browser sends one best-effort `POST /api/events/view` for that normalized handle with the current path and referrer. Rendering never waits for analytics, repeat loads of the same handle in one mounted storefront do not double-count, and tracking failures are suppressed rather than exposing server details to visitors. The backend resolves the public handle to its creator; the browser never supplies a trusted creator ID.

The authenticated dashboard uses an original cinematic dark interface: a creator-focused Home spotlight, compact navigation, high-contrast content cards, restrained hover motion, accessible focus states, and a mobile bottom navigation. The theme is scoped to the admin shell; creators' phone previews and public storefront themes remain independently customizable.

**My Store** separates storefront authoring into three focused views. **Store** manages offers, **Landing Pages** edits the public headline and visible sections, and **Edit Design** controls theme, accent color, background, button shape, and typography. The add-product dialog uses visual cards for all eight offer types and shows a live phone preview while the creator changes category, title, or price. Landing and design settings are persisted through the backend rather than existing only in browser state.

Product/service and promotion management rows expose Pin/Unpin alongside their edit, delete, and ordering controls. The live phone preview also exposes Pin/Unpin, so creators can highlight offers from either surface. Pinning persists on the server and moves published hot deals to the top of the combined phone-preview and customer-storefront feed. Draft offers display “Publish first” because unpublished content cannot appear to customers. Editing supports category, title, description, price, and draft/published status. Delete requires confirmation, and API conflicts are shown when commerce history requires the creator to unpublish instead.

The product modal is a conditional Stan-style builder rather than one generic form. All products share storefront-thumbnail and checkout sections; downloads add upload or redirect configuration, lead magnets add lead-capture and future-delivery configuration, meetings add availability, webinars add event capacity and timing, courses add modules/lessons/video and supporting assets, memberships add recurrence, and custom/community products add their fulfillment/access settings. These values and file metadata are saved through authenticated backend APIs rather than remaining browser-only. In the test storefront, a successful lead request confirms only that the details were saved and explicitly says email delivery is disabled.

The ninth visual item type, **Promotion / external link**, is an outbound offer rather than a checkout product. Creators can store brand, image URL, CTA, offer text, coupon, disclosure, schedule, publication state and order; they can edit, delete, and move promotions from My Store. The public card records an eligible click before redirecting to the merchant, and Analytics reports per-promotion clicks. Both server and browser require HTTPS destinations.

Money is displayed as INR using Indian formatting and prices are sent as paise (`priceSubunits`). Real payment surfaces are explicitly labeled. A public purchase requests an idempotent server-side checkout; disabled/misconfigured providers show that no charge was attempted. Razorpay Checkout is loaded only after the API returns a real order, and Stripe is an optional redirect strategy.

For the complete three-container workflow, start with the [infrastructure repository](https://github.com/kvsram/creator-link-store-infrastructure). Its bootstrap script clones all missing siblings, validates the laptop, starts the three containers, and runs the supported-contract smoke test. Its feature-parity matrix is the source of truth for what is complete versus a UI/API foundation.

## Regional Kubernetes deployment

The three Kustomize overlays under `deploy/overlays` target separate regional clusters. The frontend is one low-resource replica per region behind that region's ingress. Its NGINX runtime proxies `/api` only to the API Service in the same cluster, so browser traffic stays regional.

GitHub Actions publishes a GHCR image for each `main` commit. Manual promotion uses protected GitHub Environments `dev`, `preprod`, and `prod`, short-lived AWS OIDC credentials, and a self-hosted runner labeled `aws-private` that can reach the private EKS API. Configure the regional variables documented in the infrastructure repository, then use **Deploy frontend** with the exact 40-character application commit SHA plus the exact infrastructure SHA already applied to that stage. The workflow verifies the SSM release contract, copies the image to environment ECR, and only then rolls out. It intentionally cannot deploy from a public GitHub-hosted runner.
